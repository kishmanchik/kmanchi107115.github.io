02The problem

Security tooling doesn't fail by finding too little. It fails by finding too much.

Point a dozen scanners at a real codebase and you get thousands of findings: duplicated across tools, mostly unexploitable, with no indication of which two actually matter this week. Teams respond by ignoring the dashboard — which is worse than not scanning. The interesting engineering problem is not detection; it's triage, prioritisation and trust.

03How it works

A deliberate split: everything that must be reproducible is deterministic, and the model is used only where judgement genuinely helps.

01
Fan out32 adapters run across SAST, dependency/SCA, secrets, infrastructure-as-code and container analysis — in parallel, normalised into one finding model.
02
Deterministic deduplicationCross-tool duplicates are collapsed by rule, not by model. This is intentional: it means the same input always produces the same finding set, which is what makes the output auditable and diffable between runs.
03
Model-assisted analysisThe LLM layer handles what rules can't: chaining related findings into an exploit narrative, classifying severity and weakness type, and triaging likely false positives with a stated rationale.
04
Exploitability enrichmentFindings are weighted by real-world exploit-likelihood and known-exploited signals, so prioritisation reflects actual risk rather than raw severity.
05
Fix generation, then verificationProposed remediations are emitted as unified diffs — and then re-scanned inside a sandboxed container before being surfaced. A fix that doesn't actually clear the finding never reaches the developer.
06
DeliveryResults surface through a CLI, a REST API, an MCP server for agent-driven workflows, CI/CD integrations, a web UI, and IDE extensions — plus standards-compliant SARIF for anything else.

04Why it can be trusted

This is the part I care most about. A security tool that can't prove its own accuracy is just an opinion generator — and one built quickly with AI assistance has to be held to a higher standard, not a lower one.

Releases are gated by an evaluation harness

Accuracy is measured, not asserted. The suite runs against a version-pinned baseline and records recall and false-positive rate; a regression fails the release rather than shipping quietly.

  • Detection quality is a build-blocking metric, treated like a failing test.
  • Baselines are content-pinned, so "the benchmark changed" can't hide a regression.

The reproducible core is kept model-free

Deduplication and finding identity are deterministic by design. Two runs over the same commit produce the same set — which is what lets results be diffed, tracked over time and used as a merge gate.

Remediations are proven, not suggested

Every generated fix is applied and re-scanned in an isolated container. The system only proposes changes it has watched resolve the finding.

Honest self-assessment is written into the docs

The project's own documentation records where its comparisons were structurally favourable and which numbers are narrow. I'd rather a reviewer find the caveat already written down than discover it themselves.

05How it was built

Worth stating plainly, because the delivery rate invites the question.

Argus was built with an AI-agent orchestration methodology I developed — parallel subagents working in isolated worktrees against a shared, self-mined set of project invariants and reusable skills. That's how one person lands a few thousand pull requests in a matter of weeks.

The engineering that actually matters is what I put in place because of that velocity: 16,453 automated tests, an evaluation harness that fails releases on accuracy regression, a deterministic core insulated from model output, sandboxed verification of every generated fix, and documentation that records its own limitations. Speed without verification is a liability. The verification is the work.

Status. Argus is an internal, proprietary project — the source is not published. It has been dogfooded against real production services rather than distributed. Design decisions, trade-offs and the evaluation methodology are things I'm glad to discuss in detail.
